# ADR 0009 — The `postMessage` surface: typed iframe↔parent RPC + events

- **Status:** Accepted
- **Date:** 2026-06-17
- **Tags:** surfaces, transport, postmessage, browser, iframe, messageport, events, security, browser-first

> **Amendment (2026-09-17) — the peer binding is also a correctness property; a target that resolves to nothing has no peer.** The 2026-09-15 amendment's point 4 argues the `source` check from the attacker's side. It matters just as much with no attacker in the room. A page that renders several **same-origin** frames — a gallery of preview tiles, each a `blob:` document (which inherits its creator's origin) or a page off one CDN host, each with its own `channel.window` — used to hand every tile's `ready` and `content-height` to **every** channel, because every window channel listens on the one global `'message'` event and the origin cannot tell the tiles apart. Reproduced in Chromium against `1.0.0-rc.5` and against `main` before #819: two frames, two host channels, and each channel received both frames' events; a responder answered requests its frame never sent, posting the answer to its own frame; a frame's child channel accepted a sibling frame's `update` as if the host had sent it. With the binding, each channel hears only its own frame.
>
> Three things the binding rests on, now pinned by a real-browser test (`packages/core/test/browser/postmessage-window-peer.browser.ts`) as well as the node suite:
>
> 1.  **Navigation and reload keep the binding.** They keep the frame's `WindowProxy`, so `iframe.contentWindow` before and after is the same object, and a channel needs no re-subscription. That is also why the origin gate is **not** redundant beside the peer check: the same window can navigate to a foreign origin, and only the origin tells those documents apart (verified: a frame navigated cross-origin still has `e.source === contentWindow` and is dropped by the gate alone).
> 2.  **A remount does not.** A new `<iframe>` element is a new browsing context and a new `WindowProxy`, so a `Window` passed directly stays bound to the discarded one. A thunk target is resolved on every post and every inbound message, so a thunk over the element follows the remount. That is the form to use whenever the element can be replaced.
> 3.  **A target that resolves to nothing has no peer.** A thunk over a ref returns `undefined` before mount, and a detached iframe's `contentWindow` is `null`. The check as first written was `source !== peer`, which lets a `null` source equal a `null` peer and deliver: the "`null` fails closed" state of point 4, failing open. The listener now drops the message whenever the resolved target is `null` or `undefined`. Chromium did not produce a `null`-source window message in probing (3000 posts from a cross-site frame detached mid-burst all carried a live `source`), so treat this as hardening that makes the code match its stated contract, not as a demonstrated exploit.
>
> One reading changes. The `OriginOptions` envelope was described as "posting to one frame while accepting from several". Under the binding, `from` widens the **origins** accepted from `target`, never the set of windows. It is for one peer that may answer from more origins than you address it at: a popup that finishes a sign-in hop on another origin.
>
> **Amendment (2026-09-15) — the origin exemption moves OUT OF BAND; `channel.private` is added; `channel.window` drops untrusted events.** This is a **security fix**, and it corrects text below that is now wrong.
>
> The demux gate read `origin === '' || allowedOrigins.includes(origin)`, and the `''` arm is described below as the `MessagePort` exemption ("a `MessagePort` carries no origin, `''`, and skips the gate"). That was an **in-band sentinel**: a fact about the TRANSPORT (does it attribute origins?) asserted by a value travelling in the DATA channel. It was not a safe one. `''` is `MessageEvent.origin`'s own default — `new MessageEvent('message', { data }).origin === ''` — so any script sharing the page's realm could run `window.dispatchEvent(new MessageEvent('message', { data: forgedEnvelope }))` and land a forged envelope in reply-correlation, the responder registry and the event fan-out with the allow-list **never consulted**. Realistic actors: a third-party analytics or tag-manager script, or an extension content script — both routinely present on a page and neither supposed to be able to impersonate a trusted iframe. The gate was, for that one case, **weaker than the hand-rolled check it replaces**.
>
> Four changes, and the reasoning matters more than the diff:
>
> 1.  **`MessageTransport.subscribe` widens to `(data: unknown, origin: string | null) => void`.** `null` means _this transport does not attribute origins_. It is produced by CODE and is **unspellable from data**: `MessageEvent.origin` is a `USVString`, so `{ origin: null }` coerces to the _string_ `'null'` and `{ origin: undefined }` to `''` — no realm ever delivers a JS `null`. Every string, `''` included, is now an ordinary untrusted origin that must be on the list; since `Origin` is `` `https://${string}` | `http://${string}` ``, no allow-list can contain `''`, so the forged event is dropped. (`'null'`, the literal a sandboxed frame posts, stays unallow-listable for the same reason it always was.)
> 2.  **The exemption is a per-CHANNEL decision, not a per-message one.** `makeChannel`'s allow-list is `string[] | null`, where `null` means _this channel has no origin dimension_, and the gate is `allowedOrigins === null ? true : origin !== null && allowedOrigins.includes(origin)`. So a transport's `null` is honoured only by a builder that declares **no origin policy** — `channel.port`, and the new **`channel.private(transport)`** for a generic origin-less transport (an Electron IPC bridge, a worker bridge, a test fake). On a channel the caller _gated_, a `null` origin **fails closed**. This is deliberate and is [P24](../CONTRACT.md#p24--a-shared-field-name-prefix-in-a-house-contract-is-an-envelope) carve-out (b) again: had `channel.over` honoured a per-message `null`, a transport could have rendered the caller's `from` — including the deliberately fail-closed `from: []` — incapable of changing one decision, which is verbatim the inert-security-control defect #795 removed from the port builder. Better a careless transport break its own channel **loudly** (nothing is delivered) than silently open it. Strict `=== null`, never `== null` or `??`: if `undefined` also meant "no origins", a transport that merely _forgot_ the second argument would reopen the hole. House precedent for a strict `null` sentinel read by a presence check is `SchemaFingerprint.token`'s ABSTAIN value (CONTRACT.md §6).
> 3.  **`channel.window` drops any event whose `isTrusted` is `false`.** The origin change alone does **not** close the threat model above, and saying otherwise would publish a guarantee the code does not honour: `MessageEventInit.origin` is **author-settable**, so `new MessageEvent('message', { origin: 'https://app.example.com' })` reports exactly that and sails through a literal `includes`. The `''` sentinel was only the _laziest_ variant of the attack. `isTrusted` is the one bit a same-realm script cannot forge — `[LegacyUnforgeable]` in the DOM (an own, non-configurable property that survives prototype patching), `false` on every constructed event, `true` only on user-agent delivery. The check is `e.isTrusted === false`, not `!e.isTrusted`, so a polyfilled or non-DOM environment that omits the property is not silently gated out of its own channel. A harness that genuinely must synthesise events uses `channel.over` with its own transport — the seam that keeps this from being a straitjacket. Scope it honestly, though: this closes the `dispatchEvent` vector, and against a **cross-origin** peer it closes the impersonation threat, because a same-realm script cannot make the user agent stamp a foreign origin on a trusted event. Against a **same-origin** peer it closes nothing on its own — hence 4.
>
> 4.  **`channel.window` also requires the event's `source` to BE the channel's target.** `isTrusted` stops a _synthesised_ event; it does not stop the real `window.postMessage(forged, '*')`, which the user agent delivers as a genuinely trusted event stamped with the **calling document's own origin**. Where the peer is cross-origin that is harmless (the attacker's origin is not on the list). Where the peer is **same-origin** — `origins: location.origin`, which is what the scalar shorthand means when parent and frame share an origin — the forged origin _is_ allow-listed, `isTrusted` really is `true`, and before this check both guards passed the envelope into reply-correlation, the responders and the event fan-out. Reproduced in a real browser against this branch's own code. So the listener compares `e.source` to `resolveTarget()`: a message must come from the peer this channel talks to, not merely from an allow-listed origin. This is the standard control (OWASP's postMessage guidance), it holds in both directions (parent→frame `iframe.contentWindow`, frame→parent `window.parent`), and it is read in three states like the gate's own `null`: the peer passes, `null` (a dead browsing context, or a DOM that does not attribute sources) **fails closed**, an ABSENT property (a non-DOM global, an SSR pass, a polyfill) is tolerated exactly as `isTrusted === false` is. Consequence to own: a window channel now delivers only from its own `target`, so two channels on one page whose peers share an origin no longer see each other's traffic. Against a same-realm script with arbitrary execution in the page's origin this is defence in depth rather than a boundary — such a script could already act as the page — but the ADR's own claim below named the extension content script, which runs in an **isolated world** and for which this is a genuine privilege it no longer has.
>
> **Behaviour change to own, narrowly stated.** Any hand-rolled `MessageTransport` that passes `''` to mean "no origin dimension" — which is what `MessageTransport.subscribe`'s _previous_ JSDoc explicitly taught — now has every inbound message dropped on a gated channel, and must pass `null` (or move to `channel.private`). This is the real migration hazard and it is a **silent runtime** one: such a transport still typechecks. The type widening itself is essentially non-breaking (`subscribe` is declared in method position, so parameter checking is bivariant, and the inner handler is contravariant — an implementor annotating `origin: string` still satisfies the interface, pinned in `test-d`); the one residual type break is a consumer who reads `Parameters<MessageTransport['subscribe']>[0]` and dereferences `origin`, which is now possibly `null`. A Worker realm using `channel.window` for inbound `events()` would likewise start dropping parent messages (they arrive with `origin === ''`) and should use `channel.port` or `channel.private`; note this is inbound-only, because a worker's `postMessage` signature cannot accept a target origin, so no worker ever had a working `channel.window` round-trip.
>
> Read the `''` exemption as `null` throughout this ADR, and read "three builders" as four.
>
> **Amendment (2026-09-14) — the three builders are one `channel` namespace.** This ADR's entry points below are `windowChannel(opts)`, `portChannel(port)` and `channel(transport, opts)`. They are now **`channel.window(opts)`**, **`channel.port(port)`** and **`channel.over(transport, opts)`** — one exported namespace, three peer members, and the token `channel` survives as the namespace rather than as one of the three. The three names repeated the subject noun and varied only the role word, which is the cluster shape `otlp.sink`/`exporter`/`json` and `secrets.register`/`has`/`redact` already replaced: one name per dimension, the role named at the call site. `over` is taken from this ADR's own wording — "over any `MessageTransport`". The namespace is **not itself callable**: [P12](../CONTRACT.md#p12--envelope--scalar-shorthand) reserves a bare call for the DOMINANT case, and the generic transport builder is the rare one (its only in-repo callers are tests), so making it bare would invert the hierarchy. Cost, stated: a namespace pins all three members for any consumer of one — esbuild will not split an object literal to drop a dead half — so a `channel.port`-only consumer now carries the origin-validation apparatus that `portChannel` deliberately had none of per #795. The `postmessage` subpath is not budgeted, so no gate moves; names freeze at the stable tag while bytes stay recoverable (split the subpath later). Read `windowChannel` as `channel.window`, `portChannel` as `channel.port` and `channel(` as `channel.over(` throughout this ADR; every decision it records is otherwise unchanged.
>
> **Amendment (2026-09-14) — the channel's origin policy is one `origins` envelope.** The signatures below say `windowChannel({ target, targetOrigin, allowedOrigins? })`, `portChannel(port, { allowedOrigins? })` and `channel(transport, { allowedOrigins })`. Two of those have moved. `portChannel` lost its origin list entirely in #795 (a port always delivers origin `''`, so the option could never change a decision — [CONTRACT.md P24](../CONTRACT.md#p24--a-shared-field-name-prefix-in-a-house-contract-is-an-envelope) carve-out (b)). And `targetOrigin`/`allowedOrigins` were one dimension spelled as two fields — the tell is right here in Decision 1, where one is documented as the other's default — so they fold into **`origins: Origin | OriginOptions`** (`{ to, from? }`, `from` defaulting to `[to]`), with the bare origin as the P12 scalar shorthand for `{ to: X, from: [X] }`. `channel()` takes the inbound half alone, under that half's own name ([P1](../CONTRACT.md#p1--one-word-one-concept-one-value-space)/[P16](../CONTRACT.md#p16--cross-surface--cross-package-parity)): `from: Origin | Origin[]`, the same name and value-space as `OriginOptions.from`. It is deliberately NOT spelled `origins` — that would be one token over two incomparable value-spaces (an array is legal on `channel`, a compile error on `windowChannel`, and the scalar shorthand would mean `{ to: X, from: [X] }` on one and `[X]` on the other), which is the P1 collision an envelope avoids rather than creates. No silent failure mode either way: every divergence is a compile error. `target` stays flat beside it — it is the transport handle, not part of the policy. Hard break, no alias (P19, rc channel). Read `targetOrigin` as `origins.to` and `allowedOrigins` as `origins.from` throughout this ADR; every decision it records is otherwise unchanged.
>
> Two points in the **Security model** below are sharper than they were. The inbound list is now typed `Origin`, not `string` — so `allowedOrigins: '*'`, which used to typecheck and then silently drop **every** inbound message (the gate is a literal `includes`, not a wildcard match), is a compile error. The `Origin` type cannot express the rest of that trap, though: `'https://*.example.com'`, `'https://app.example.com/'`, `'https://App.Example.com'` and `'https://app.example.com:443'` all satisfy the template literal and all still match nothing. So the construction-time guard that threw on `targetOrigin === '*'` now runs over **both** halves and rejects any authored origin that is not `new URL(x).origin` — the browser's own normaliser — with the corrected spelling in the message. Failing loud at construction replaces failing silent at the first message.
>
> One consequence is deliberate and worth naming: a **sandboxed** iframe posts with the literal origin `'null'`, which is not an `Origin` and cannot be allow-listed. That is the intended answer — every sandboxed frame from every source shares `'null'`, so allowing it is close to allowing everything — and the surface already ships the right primitive for that case: hand the frame a `MessagePort` and use `portChannel`. A port is gated by who you hand it to, which is the only gate that means anything when the origin is not unique.

> [!NOTE]
>
> This rides the surface model ([ADR 0005](./0005-surfaces-and-the-authoring-model.md)) and the transport-replacing `Surface.execute` hook ([ADR 0008](./0008-non-http-surfaces-and-pipe.md)) — the same machinery `shell` and `llm` use — plus the run-identity spans of [ADR 0007](./0007-composition-causality-and-run-identity.md). The load-bearing decision is the **security model**: origin is first-class and gated **before** any dispatch or validation, the "structural, not advisory" bar that rejected `inferBearer` in #6 and shaped the `shell` surface.

## Context

The browser's `postMessage` is how a page talks to an iframe it embeds (or that embeds it), to a popup, to a Web Worker, or across a `MessageChannel`. It is _also_ a perennial source of three bugs, every one of which StitchAPI exists to remove:

1.  **Drifted contracts.** The two sides agree on a message shape by convention — `{ type: 'focus', payload: … }` — written twice, in two codebases, with nothing checking they still match. The receiver reads `e.data.user.id` and one rename later it is `undefined`. This is exactly the response-shape drift `output` validation catches for HTTP, with no equivalent on the message bus.
2.  **No validation.** `e.data` is `any`. A handler trusts whatever crossed the wire — wrong types, missing fields, a hostile peer's payload — because there is no schema between the `MessageEvent` and the application code.
3.  **`postMessage('*')` with no origin check.** The single most common postMessage vulnerability: posting to (or accepting from) `targetOrigin: '*'`, which leaks the message to whatever document currently occupies the frame and accepts a reply from anywhere. The browser API makes the unsafe path the easy path — `'*'` is one character shorter than the right answer.

A fourth, smaller waste: `postMessage` carries no request/response correlation. Every RPC-over-postMessage reinvents a `{ id }` field and a pending-promise map by hand, usually subtly wrong (no timeout, no abort, leaks the pending entry on a dropped reply).

The `Surface` model already has the two pieces this needs. `Surface.execute` ([ADR 0008](./0008-non-http-surfaces-and-pipe.md)) lets a surface **replace the transport** at the engine's adapter call site, _inside_ the resilience chain, so `retry`/`throttle`/`circuit`/per-attempt `timeout`/`signal`/`trace`/`auth`/`hooks` all wrap it. `Surface.stream` ([ADR 0005](./0005-surfaces-and-the-authoring-model.md) Decision 12) marks a surface streaming and decodes a live body into `delta` chunks. A `postMessage` RPC is a custom transport (`execute`); a `postMessage` event subscription is a stream (`stream`). Nothing in the core engine needs to change.

## Decision

**Ship a `postMessage` surface family behind a `stitchapi/postmessage` core subpath** — typed, validated, observable RPC + events over a `Window`, an iframe's `contentWindow`, or a `MessagePort`, riding `Surface.execute` / `Surface.stream`.

1.  **A `channel` abstraction binds the transport + the security policy at construction.** The browser primitive (where messages go, what origin they must carry) is _not_ a per-call concern — it is the channel's identity, bound once, exactly as a seam binds `baseUrl`/`auth` once. The entry points are `windowChannel({ target, targetOrigin, allowedOrigins? })` (a `Window`, or a `() => Window` thunk for a frame that mounts late), `portChannel(port, { allowedOrigins? })` (a `MessagePort`), and the low-level `channel(transport, { allowedOrigins })` over any `MessageTransport` (the in-memory seam the tests drive). A `MessageTransport` is the one small interface between this surface and a concrete primitive — `post(message, transfer?)` + `subscribe(handler) → unsubscribe` — which is what lets the whole surface be exercised over a fake linked pair with no DOM.

2.  **Four verbs, two surface ids.** A `PostMessageChannel` mints:

    - **`request(opts)`** — correlated request→response. A **buffered** surface (`id: 'postmessage'`) whose `execute` mints an id, posts `{ type, id, payload }`, registers a pending entry, and resolves when the matching `{ type: reply, id }` lands (`reply` defaults to `` `${type}-result` ``). The reply payload is the value; `output` validates it.
    - **`emit(opts)`** — fire-and-forget. The same buffered surface, but `execute` posts `{ type, payload }` (no id) and resolves immediately; result `void`.
    - **`events(opts)`** — inbound event subscription. A **streaming** surface (`id: 'postmessage-event'`) whose `execute` hands the engine a live `ReadableStream` the channel feeds; `await` resolves to the collected payload array, `.stream()` yields live deltas; `output` validates each payload (per-`delta`, [ADR 0005](./0005-surfaces-and-the-authoring-model.md) Addendum).
    - **`respond(type, handler, opts?)`** — the **receiving** side (e.g. an iframe answering a parent's `focus`). Origin-gated, validates the inbound payload against `input`, runs `handler`, validates the result against `output`, posts `{ type: reply, id, payload: result }`. It is the only verb that is **not** a stitch — it makes no outbound call, so it returns a plain unsubscribe.

    The registry — the pending-request map, the responder map, the event-subscription set — lives **per channel**, behind a **single** demux listener attached once at construction (the decision: per-channel, not per-surface; one listener, not one per stitch). `close()` detaches it, rejects every pending request, and ends every event stream.

3.  **The demux gates origin FIRST.** On each inbound `(data, origin)` the channel: (1) **origin-gates** — an origin not in `allowedOrigins` is dropped _before_ anything else (a `MessagePort` carries no origin — its transport reports `origin: null` and the builder declares no allow-list, so there is no gate to skip; a port is already a private capability); (2) shape-guards `{ type: string }`; (3) correlates a **reply** by id _and_ type; (4) dispatches to a **responder** (validate inbound → run → validate result → post reply); (5) fans to matching **event** subscriptions; (6) drops the unmatched. Gate-before-validation is the security bar, not an optimisation (Decision 5).

4.  **Correlation, timeout, and abort reuse the resilience chain — no bespoke timer.** `request`'s `execute` wires the engine's per-attempt `signal` (which `withTimeout` aborts on `timeout`, and a caller's `signal` aborts on cancellation) to reject-and-deregister the pending entry. A request with no matching reply therefore rejects via the engine's `timeout`/`signal`, surfacing as an ordinary `StitchError` — the concrete payoff of [ADR 0008](./0008-non-http-surfaces-and-pipe.md) Decision 1, identical to how `shell` gets timeout/cancel for free. No second timer is invented.

5.  **A core subpath, not a peer package.** Unlike `shell` (Node-only, quarantined out of core), `postMessage` is the **most browser-native capability StitchAPI has** — it needs nothing but `postMessage`/`MessageEvent`/`MessagePort`/`ReadableStream`/`globalThis.crypto`. So it ships as a core subpath (`stitchapi/postmessage`), reached only through `cfg.kind`, exactly like `sse`/`stream`/`graphql`. The root entry never imports it.

## How it holds the three gates

- **browser-first** — the module uses only browser-native APIs; no `node:*`, no `Buffer`. It is pinned in the `browser-bundle.spec` matrix both as a `BROWSER_LEGIT` subpath and in the streaming-surface set (its `events` verb carries a `stream` hook), asserting it bundles for `"browser"` with no `node:*` and no `EventSource`.
- **bundle-frugal** — reached only through the `stitchapi/postmessage` subpath; `import { stitch }` pulls in none of it (the engine reaches the surface via `cfg.kind` at runtime, never a static import).
- **contract-not-dependency** — `kind` round-trips to its `id` string on `__config` ([ADR 0005](./0005-surfaces-and-the-authoring-model.md) Decision 11): `'postmessage'` for request/emit, `'postmessage-event'` for events, both valid JSON. The live `execute`/`stream` hooks and the target `Window` are redacted, never serialised. The non-serializable bits — a `Window` thunk, a `MessagePort` instance — are acknowledged **sugar** in the exact category the library already draws the line at (`transform`, `paginate.next`, `cache.key`, `pipe`'s step mapping): the channel's _binding_ is sugar; a stitch's _declaration_ (its `kind` id, `type`, schemas) serializes.

## Security model

Origin handling is **structural, not advisory** — the bar that rejected host-inferred bearer tokens in #6 and that the `shell` surface set for command injection:

- **The `Origin` type forbids `'*'`.** `Origin = ` `` `https://${string}` | `http://${string}` `` — `'*'` is not assignable to either arm, so a wildcard `targetOrigin` is a **compile error**, not a lint warning. The unsafe path is unspellable in typed code.
- **`windowChannel` also throws at runtime on `'*'`** — defense in depth, so an `as any` cast past the type still fails fast at construction rather than leaking the first message.
- **The gate runs before dispatch and before validation.** A message from a disallowed origin is dropped in step 1 of the demux — never correlated to a pending request, never handed to a responder, never validated, never delivered to an event stream. An attacker on the wrong origin learns nothing from timing or from a validation error, because neither runs.
- **The list is COPIED at construction.** `originList` returns `[...list]`, never the caller's own array, so a later `push` cannot retarget a live channel's gate — which also matters because `assertOrigin` runs only over the elements present at construction, so an entry added afterwards would be honoured by the gate while the same string passed to the constructor throws.
- **An empty `allowedOrigins` over an origin-bearing transport fails closed** (drops everything) — a misconfigured channel is silent, not promiscuous. Nothing on the wire can widen it: a transport claiming "no origin dimension" (`origin: null`) on a _gated_ channel fails closed too, so `from: []` is a list the caller can actually rely on.
- **`MessagePort` is exempt by construction — and the exemption is OUT OF BAND.** A port is a private, already-handed-out capability with no origin; gating it would be theatre. What matters is _how_ the exemption is expressed: the channel is built with **no allow-list at all** (`channel.port` / `channel.private` take no origin policy), and the transport reports `origin: null` from code. It is never a value the data channel can assert. It used to be `''`, which the data channel _could_ assert — see the 2026-09-15 amendment; do not reinstate it.
- **`channel.window` drops synthesised events.** `MessageEventInit.origin` is author-settable, so an origin allow-list alone cannot distinguish a same-realm forgery from a genuine peer message. An event whose `isTrusted` is `false` is dropped before the origin gate runs. That stops `dispatchEvent(new MessageEvent(…))` from impersonating **a cross-origin peer** — the attacker cannot make the user agent stamp a foreign origin on a trusted event.
- **…and requires the event's `source` to be the channel's own target.** `isTrusted` alone is not enough when the peer is **same-origin**: a third-party page script or an extension content script can call the real `window.postMessage(forged, '*')`, which is delivered genuinely trusted and stamped with the page's own origin — allow-listed, by construction, whenever `origins` names that origin. `e.source === resolveTarget()` is the check that separates the peer from every other window in the realm, in both directions. `null` (a dead browsing context, or a DOM that does not attribute sources) fails closed; an absent property is tolerated, for the same reason `isTrusted` is compared `=== false`.

A responder DROPS a payload that fails its `input` schema rather than replying with an error (a hostile peer learns nothing from the reply shape), and never posts a result that fails its `output` schema (an off-contract reply is suppressed, not sent).

## Observability (ADR 0007)

Every verb is an ordinary stitch run, so each gets a run-identity span ([ADR 0007](./0007-composition-causality-and-run-identity.md)) and the full `start → request → (delta…) → result → done` event spine for free: a `request`'s `start`/`result`, an `events` subscription's per-payload `delta`s, a drift finding when a payload violates `output`. A `postMessage` exchange becomes visible in the same trace/DAG as an HTTP call — the message bus stops being a blind spot.

## Consumer notes (two sharp edges, by design)

Surfaced by the first real adoption (strimko's template-preview channel) — documented here so they are not a surprise:

- **A stitch is a lazy result — drive it.** Every verb returns a stitch whose call yields a _cold_ `StitchResult`: the run (and thus the `postMessage`) happens only when the result is driven — `await` / `.then` / `.catch` / `.finally`. For `request`/`events` you naturally `await`/`.stream()`, so this is invisible; for fire-and-forget **`emit`** you must drive it explicitly — `void send(input).catch(() => {})` — or nothing is posted. The strimko host uses exactly this idiom for `template/update`.
- **`events` validation terminates the stream.** `output` on `events` validates each payload per-`delta`, and a violation ends the subscription with a `drift` error — the same loud-not-silent contract as `sse`/`stream`. That is right for a coherent stream but surprising for a _discrete_ event bus, where one malformed message should not kill the channel. There, omit `output` and validate each payload in the consumer (drop the bad one, keep listening) — the pattern the strimko `template/content-height` and `template/update` subscriptions use. A built-in `onInvalid: 'drop'` mode for `events` is noted as future work.

## Alternatives considered

- **Overload the user `adapter` instead of a surface.** Rejected for the same reason [ADR 0008](./0008-non-http-surfaces-and-pipe.md) rejected it for `shell`: `adapter` is the user's HTTP-client slot. A `postMessage` channel is a protocol with its own request shaping, correlation, and a stateful registry behind a single listener — that is a `Surface` identity (`buildRequest` + `execute`/`stream` bundled with the `id`), not a transport swap. Overloading `adapter` would also lose the per-channel registry and muddy redaction.
- **A full RPC `serve`-style responder primitive.** `respond` is deliberately the **minimal** responder — register one handler per `type`, validate-in/validate-out, reply. A richer surface (a routed responder table, method namespaces, a `serve`-style declarative receiver, schema-negotiated handshakes) is **future work**; it is not needed to remove the three bugs in Context, and shipping the minimum keeps the first version reviewable. The channel abstraction leaves room for it (a responder registry already exists per channel).
- **Use `EventSource`-style auto-reconnect / replay for `events`.** Out of scope, mirroring the `sse` decision: a dropped channel is the caller's to re-establish; buffering/replay is a separate concern.
- **A single callable default export** (à la `sse(config)`). Rejected: `postMessage` has _four_ verbs (request/emit/events/respond) with no single "the call", and the transport+origin must be bound before any of them. The **channel factory is the entry point**; the builders and the two `Surface` identities are the named exports.

## Gates

- **browser-first** — only browser-native APIs; pinned in the `browser-bundle.spec` matrix (both legit-subpath and streaming-surface), no `node:*`, no `EventSource`.
- **bundle-frugal** — subpath-only; `import { stitch }` pulls in none of it.
- **contract-not-dependency** — `kind` round-trips as its `id` (`'postmessage'` / `'postmessage-event'`); live hooks + the target `Window`/`MessagePort` are redacted sugar, the channel's binding being in the same category as `transform`/`pipe`.
- **security** — origin is a first-class, non-`'*'` type **and** a runtime guard; the gate runs **before** correlation/validation/delivery; responders fail closed on bad input/output; `MessagePort` is exempt by construction, with that exemption expressed **out of band** (no allow-list on the channel, `origin: null` from the transport) rather than as a sentinel value on the wire; `channel.window` additionally drops events whose `isTrusted` is `false`.
