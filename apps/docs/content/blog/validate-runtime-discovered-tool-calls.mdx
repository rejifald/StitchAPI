An agent rarely knows its full toolset at compile time: it reads an MCP server's `tools/list`, pulls a tenant's enabled plugins, or fetches an OpenAPI spec from a URL — and every tool arrives as JSON Schema you didn't have when you built.

## The type you're chasing can't exist

Code generation assumes the tools are known when you build. Tools loaded from a running MCP server or a spec behind a URL aren't, so per-tool static types are off the table. The autocomplete you're mourning was never on offer either: an editor can't complete against a schema that isn't present while you write the code. The type assertions pile up because you keep asserting a shape you don't actually know.

So stop typing across the boundary and validate at it. The model returns arguments as JSON; you hold the tool's JSON Schema; you check one against the other at call time. Past that check the data is `unknown` until you narrow it where you use it — and `unknown` you narrow on purpose beats `any` you cast on reflex.

**Validate at the boundary, not across it.**

## Turn the discovered schema into a validator

`tools/list` — or the spec, or the plugin manifest — hands you an OpenAI-compatible JSON Schema. `jsonSchemaValidator` turns it into a [Standard Schema](https://standardschema.dev); `toValidator` gives you one `validate()` that returns a result and never throws.

```ts twoslash
// @noErrors
import { jsonSchemaValidator } from '@stitchapi/json-schema';
import { toValidator } from 'stitchapi';

// `tool.parameters` is the JSON Schema you read at runtime — no static shape until now.
const validate = toValidator(jsonSchemaValidator(tool.parameters));

const result = await validate.validate(modelArgs);
if (result.ok) {
    runTool(result.value); // `unknown` — narrow it where you read it
}
```

One interface spans every source. A tool you hand-wrote and described with Zod and a tool you read off an MCP server and described with JSON Schema become the same `validate()` call. **Standard Schema, not a Zod lock-in** — Valibot, ArkType, and a raw JSON Schema all arrive through the same door.

## Hand the model its own mistakes

The value isn't the boolean; it's the shape of the failure. `validate()` returns issues as `{ path, message }` — a list you feed straight back to the model, not a `ZodError` you catch, stringify, and hope reads well in a prompt.

```ts twoslash
// @noErrors
const result = await validate.validate(modelArgs);
if (!result.ok) {
    // result.issues → [{ path: ['limit'], message: 'must be <= 50' }]
    return toolMessage(
        result.issues
            .map((issue) => `- ${issue.path.join('.') || '(root)'}: ${issue.message}`)
            .join('\n'),
    );
}
```

A per-path rejection is a repair instruction: the model reads that `limit` must not exceed 50, drops the offending field, and calls again. A thrown exception is a dead end. **Structured feedback the model can act on, not a stack trace it can't.**

## The tool runs a call you didn't write

A discovered tool almost always fronts a remote call — the MCP server proxies one, the plugin posts to its own API, the OpenAPI operation names an endpoint. When you hold the response schema too (an OpenAPI operation carries both), the same schema takes a second job. Run the call as a stitch, anchor its response to that schema, and `inspect()` reports where the live service returned something its own contract never promised — a field that appeared, a number that came back a string, a null where the schema said otherwise.

```ts twoslash
// @noErrors
import { jsonSchemaValidator } from '@stitchapi/json-schema';
import { stitch } from 'stitchapi';

const callTool = stitch({
    url: tool.endpoint,
    method: 'POST',
    output: jsonSchemaValidator(tool.responseSchema),
});

const inspection = await callTool.inspect({ body: modelArgs });
inspection.value; // validated response, or null on a hard failure
for (const finding of inspection.findings) {
    // e.g. { path: 'items[].sku', change: 'undeclared' }
    log.warn(`response drift at ${finding.path}: ${finding.change}`);
}
```

The spec told you what the tool claims to accept and return. Drift tells you when the running service stops honouring that claim — the failure mode a tool you discovered, and never compiled against, has and a hand-written one rarely does.

## Validate where you know, type where you don't

A discovered tool has no compile-time shape, so the compiler can't guard it and pretending it can costs you casts. A validator can guard it: it turns the model's JSON into either data you narrow or errors you return. One Standard Schema interface covers the tools you write and the tools you load; one `validate()` gives you the same result shape for both; the same schema that checks the model's arguments also catches the service drifting underneath them.
