You fetch an order, then its shipment, then the carrier's tracking — and the tracking call needs the shipment's code **and** the order's region, two hops back. Written as plain `await`s, that's already clean: each [stitch](/docs/concepts/the-stitch) is typed and validated, so `order` and `shipment` are real typed variables and an ancestor two steps back is just… a variable still in scope.

The one thing plain `await`s drop is the **trace**. Each bare call mints its own root run, so those three calls are three _unrelated_ operations — nothing ties them together when one fails at 2am. [`pipe()`](/blog/compose-api-calls-into-a-pipeline) fixes that by building the chain as a value. `linked()` fixes it the other way: it opens a **run scope** and lets you keep writing the plain `await`s.

## The scope

```ts twoslash
import { stitch } from 'stitchapi';
import { linked } from 'stitchapi/pipe';
import { z } from 'zod';

const Order = z.object({
    id: z.number(),
    shipmentId: z.string(),
    region: z.string(),
});
const Shipment = z.object({ carrier: z.string(), trackingCode: z.string() });
const Tracking = z.object({ events: z.array(z.string()) });

const fetchOrder = stitch({
    url: 'https://api.example.com/orders/{id}',
    output: Order,
});
const fetchShipment = stitch({
    url: 'https://api.example.com/shipments/{id}',
    output: Shipment,
});
const fetchTracking = stitch({
    url: 'https://api.example.com/tracking/{carrier}/{code}',
    output: Tracking,
});
// ---cut---
const tracking = await linked(async (run) => {
    const order = await run(fetchOrder, { params: { id: 1043 } });
    const shipment = await run(fetchShipment, {
        params: { id: order.shipmentId },
    });
    return run(fetchTracking, {
        params: { carrier: shipment.carrier, code: shipment.trackingCode },
        query: { region: order.region }, // two hops back — just a variable
    });
});
```

`linked(body)` hands your `body` a `run`. Call your stitches through it instead of directly, and that's the whole API.

-   **`order` is `Order`, `shipment` is `Shipment` — no casts.** `run(stitch, input)` is typed straight from the stitch: the input is the stitch's own input, the result its own output. Reaching an ancestor two hops back (`order.region`) isn't a feature you invoke; it's a variable you already have.
-   **The calls share one trace.** Each `run(...)` chains as a child of the call before it, so the trace draws the same `fetchOrder → fetchShipment → fetchTracking` chain `pipe` does — not three loose calls. (`order` is the scope's root run; `shipment` a child of `order`; `tracking` a child of `shipment`.)
-   **It fails fast.** A rejected call rejects the whole `linked(...)` and the body stops — the same one-rejection-at-the-boundary you get from `pipe`, except the boundary is the `await` you already wrote.

## Concurrent steps stay in the trace

When two calls inside the scope _don't_ depend on each other, don't `await` them in series — hand `run` an [`all`](/blog/run-api-calls-in-parallel). `run` accepts any combinator as a node, so the parallel fan nests inside the same trace:

```ts twoslash
import { stitch } from 'stitchapi';
import { all, linked } from 'stitchapi/pipe';
import { z } from 'zod';

const Order = z.object({ id: z.number(), shipmentId: z.string() });
const Shipment = z.object({ carrier: z.string() });
const Invoice = z.object({ total: z.number() });
const fetchOrder = stitch({
    url: 'https://api.example.com/orders/{id}',
    output: Order,
});
const fetchShipment = stitch({
    url: 'https://api.example.com/shipments/{id}',
    output: Shipment,
});
const fetchInvoice = stitch({
    url: 'https://api.example.com/invoices/{id}',
    output: Invoice,
});
// ---cut---
const summary = await linked(async (run) => {
    const order = await run(fetchOrder, { params: { id: 1043 } });
    // shipment and invoice are independent — fan them out, still inside the trace
    const { shipment, invoice } = await run(
        all({ shipment: fetchShipment, invoice: fetchInvoice }),
        { params: { id: order.shipmentId } },
    );
    return {
        orderId: order.id,
        carrier: shipment.carrier,
        total: invoice.total,
    };
});
```

## `linked` or `pipe`?

They cover the same need from opposite ends, and both ship:

-   **`pipe(...)`** makes the chain a **value** — `const flow = pipe(a, b)` is a reusable callable you can store, pass around, or nest inside `all`/`any`/`race`. Reach for it when the composed flow is itself a thing you hand to other code.
-   **`linked(body)`** makes the chain **code** — the plain `await`s you'd write anyway, fully typed, with the trace added. Reach for it when you're just running a dependent flow once and want it to read like ordinary async code.

Neither is a workflow engine: the shape is fixed when you write it, `run` only adds trace linkage, and it composes the stitches you already declared without changing how any one behaves alone — [runtime stitching, not a workflow platform](/blog/runtime-stitching-vs-workflow-platforms).

## Try it

```package-install
stitchapi
```

`linked` lives at the `stitchapi/pipe` subpath, so it only enters your bundle when a flow needs it. Each call is a [stitch](/docs/concepts/the-stitch) with its own [validation](/blog/validate-api-response-zod) and resilience, the whole scope shows up in the [event stream](/docs/concepts/event-stream), and a failure anywhere rejects with a [typed error](/blog/typed-errors-without-try-catch).
